# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A layout simulator ("佈局模擬器") for the game 口袋學院物語2 (Pocket Academy 2), letting players plan school maps on a tile grid and see which "人氣景點" (popularity spots) their layout produces. The entire app is a single self-contained file, `index.html` — HTML, CSS, and vanilla JavaScript with no build step and no dependencies to install. **After any change, run `node scripts/check.js`** — it validates JS syntax and data consistency (icons/JP-names coverage, spot & dev-guide id integrity, built-in map shapes, share-code roundtrip); all checks must PASS. The entry point is fixed (`/pa2-check` and both CLAUDE.md files reference it) but the logic lives in `scripts/checks/{parse,sim,consistency}.js`: `sim.js` holds the original 8 groups (PASS/FAIL), `consistency.js` holds the cross-file checks added in B0 — `SPOTS`/`items`/`ITEM_ICONS`/`JP_NAMES` versus `db/data.js` row-by-row, `sim/presets/*.json` versus the embedded `PRESET_*_DATA`, `scripts/typekeys.lock` (the append-only guard for the share-code ABI — append new ids there, never reorder), the 8 on-site share codes' decode→encode roundtrip, `DEV_GUIDE`'s `cond`↔`needs` agreement, and per-page visible word count. Those land as **WARN** (three levels now: PASS/WARN/FAIL); `--strict` promotes WARN to FAIL, `--verbose` prints full lists. The measured numbers at lock-in time are in `scripts/BASELINE.md` — a changed number that nobody intended is a regression. `scripts/checks/sim.js` deliberately keeps its own mirror of `encodeMap`/`decodeMap` rather than requiring the engine: sharing them would make the checker break in lockstep with the encoder and still report PASS. Project skills: `/pa2-check` (run the checker) and `/add-facility` (the standard workflow when the user reports a facility size, rename, or missing facility). Tailwind CSS and Google Fonts are loaded from CDNs, so the page needs internet access to render correctly.

To run: open `index.html` in a browser (e.g. `start index.html` from PowerShell). UI text is Traditional Chinese (zh-TW). Deployed to GitHub Pages (the `index.html` name is required for that). `<head>`'s canonical/og:url/og:image are live values now (`https://ploglin.cc/kairosoft/school2/sim/`; the og:image is the game card baked by `scripts/gen-og.js` — don't hand-edit those three, `node scripts/gen-og.js --stamp` owns og:image and `scripts/link-check.js` asserts all three). Touch input is supported (tap paints, drag paints continuously, long-press is the eyedropper) and the layout stacks vertically under 768px. The map can also be shared via URL hash (`#m=` + RLE/base64url of the grid, see `encodeMap`/`decodeMap` — TYPE_KEYS order must stay append-only; non-26×24 maps carry a `RxC;` size prefix inside the code, 26×24 stays prefix-free for backward compatibility).

## Architecture (all inside 2.html's single `<script>` block)

- **`items`** — registry of every placeable tile type (id, display name, one-character `short` label, color, palette category `type`, optional `textCol`). Categories map 1:1 to the sidebar palette sections: `tool`, `env` (環境地形), `fac` (生活與設施), `spec` (教室與專科), `sports` (運動與社團), `farm` (動植物農牧). Adding a new building = adding one entry here; the palette renders itself from this object.
- **`SPOTS`** — the game's official 29 popularity spots (sourced from the カイロパーク攻略 Wiki). Each `req` entry is an item id or an array of ids meaning "any one of these" (e.g. 森林/櫻花樹). A spot forms when all three required facilities touch a common **4×4 window** (`checkSpots()`); the designated area is then each required facility's tiles in that window plus a 1-tile ring (2-tile ring for footprints ≥4 cells). `bonus` holds the attribute gains (文系/理系/體育/頭腦/運動/人氣/態度) and optional `teacher` the recruitable teacher(s), both shown in the hover tooltip.
- **`HANDBOOK`** — static in-game reference data (attack tips, school ranks, teachers, clubs, careers, events, special lessons, challenges, items) rendered as a tabbed modal via `buildHandbook(section)`, sharing the `reportModal` shell with `buildReport()` and `buildDevGuide()` (which lists facility unlock conditions per school-rank stage, auto-checking "×N prerequisite" counts against the map via `countBuilt()`). All data sourced from the カイロパーク攻略 Wiki. `JP_NAMES`/`SPOT_JP` map item/spot ids to Japanese names (shown in palette tooltips and the handbook's 中日對照 tab); the UI itself stays Traditional Chinese. The `<head>` carries SEO meta (description/keywords/Open Graph/JSON-LD WebApplication). Marked tiles get a yellow ring and colored indicator dots — **except in locate mode** (see below), where every spot channel is suppressed.
- **`gridData`** — the single source of truth: an array of `{ type, elevation }` sized per town (in-game coords start at [2,2], so cell count = max coord − 1: 健康鎮 26×24、湖岸小鎮 24×24、冬郵/溪谷/百靈 26×26; `gridRows`/`gridCols` are mutable, switched via `setGridSize()` or automatically when loading saves/share codes of another size). All rendering (`updateTileVisuals`, `updateSpotIndicators`) reads from it; `applyTool` writes to it and re-runs `checkSpots()` over the whole grid.
- **Coordinate system**: internal indices are `r` / `c`, displayed axis labels replicate the game's coordinates — X = `r + 2` (top to bottom) and Y = `gridCols + 1 - c` (left to right, descending). Matches 健康鎮; offsets for other towns to be confirmed in-game. Keep this mapping in mind when translating between on-screen labels and array indices.
- **Elevation**: each cell has `elevation` 1–3 (平地/高地1層/高地2層), chosen via `setElevation()` and applied when painting. Slopes are **derived, not stored**: `isSlope(r,c)` — an empty cell whose elevation is exactly one above a 4-neighbor (game rule: the whole boundary becomes slope, on the higher tile; a 2-level gap is a cliff). Slope cells get striped styling (`.slope-tile`), count as the `slope` item in spot checks (黃昏 spot), and the `slope` item is `hidden: true` — never placeable from the palette.
- **Persistence**: named saves go to `localStorage` under the key `pa2_maps_v9`. UI preferences (diamond view, selected tool, elevation, last save name) persist in `pa2_prefs_v1`; the canvas autosaves (debounced) to `pa2_autosave_v1` after every change and is restored on startup — the 健康鎮 preset only loads when no autosave exists. `PRESETS` lists the game's 5 towns (健康鎮/冬郵小鎮/湖岸小鎮/溪谷小鎮/百靈山丘) and all five now carry user-transcribed terrain data: 健康鎮 (`PRESET_DEFAULT_DATA`), 冬郵小鎮 (`PRESET_EAST_DATA`), 湖岸小鎮 (`PRESET_LAKE_DATA`, 24×24), 溪谷小鎮 (`PRESET_VALLEY_DATA`, 26×26), 百靈山丘 (`PRESET_HILL_DATA`, 26×26) — east/lake/valley/hill are mirrored in `sim/presets/*.json` (single-line, no `bid`; keep both copies in sync). The `data: null` → blank-canvas fallback in `loadPreset` remains for safety but no town uses it now. The lake map's `pool` footprint (X18-19 × Y10-9) was confirmed in-game 2026-07-31 and the preset carries the full 2×2. Chosen from the `townBtn` → `townPop` list panel (a hand-built panel, **not a `<select>`**: the old `presetSelect` said the wrong thing after you cancelled the confirm dialog, and re-picking the same town fired no `change` event at all → deadlock. The button label is derived from state, so there is no `value` that can disagree with the canvas). Loaded with `loadPreset(key)`; `matchTown()` recognises the current grid so a share code of a non-preset size shows as e.g.「自訂 26×22」instead of lying about which town you are on. The player's in-game progress lives in normal localStorage saves; `seedProgressSave()` injects a one-time "健康鎮進度" save from `PROGRESS_SEED_DATA` on first launch. On startup the 健康鎮 preset is auto-loaded.
- **Responsive grid**: tile size is driven by CSS vars `--tile`/`--axis`; `fitGrid()` recomputes them on load/resize so the whole map fits the viewport without scrollbars. A fixed `#coordHint` bar shows the hovered tile's game coordinates, type, and elevation (updated in the tile `mouseenter` handler and `applyTool`).

Painting works by mousedown + drag (`isDrawing` flag with `mouseenter` on tiles). Additional editing tools: rectangle fill (`rectMode` toggle or Shift+drag, 1×1 items only, commits on mouseup), right-click eyedropper (`contextmenu` → `selectTool`), and whole-building erase (empty tool on a cell with a `bid` removes every cell sharing that bid). `exportImage()` renders gridData to a canvas and downloads a PNG. `buildReport()` opens a modal summarizing active spots, total attribute bonuses (parsed from `bonus` strings), near-miss spots, and blocked-building count (`lastSpotStats`/`lastBlockedCount` are cached by `checkSpots`/`updateAccessWarnings`). Saves in `pa2_maps_v9` are stored as `{data, ts}` (legacy plain-array entries still load); the `loadBtn` → `loadPop` panel lists them with timestamps plus a rename button, and holds **one** `#pasteBox` that sniffs all three accepted formats (share link / bare `#m=` code / legacy JSON) — the separate 匯出/匯入 JSON buttons are gone, since `#m=` round-trips the same grid including per-building `bid` grouping. Each stroke pushes a full-grid JSON snapshot onto `undoStack` (`pushHistory()`, Ctrl+Z / Ctrl+Y, max 60). Multi-tile buildings get a per-placement `bid` (block id) stored in their cells; `sameBlock()` uses it to render one building as a merged block (box-shadow fills the grid gaps, label only on the top-left cell), and `assignBlockIds()` retrofits bids onto presets/old saves by greedily matching w×h chunks. `checkSpots()` also feeds the sidebar stats panel (`renderSpotStats`: active spots + near-miss "differ by one facility" list). The `◆ 視角` button toggles `body.diamond` — the grid rotates 45° via CSS (labels counter-rotated) to mimic the game's isometric view, with `fitGrid()` sizing the rotated square.

### Rules that were violated once and now have code behind them

- **Overwriting a cell must demolish the whole building under it.** `applyTool()` and `commitRect()` both call `razeUnder(r, c, w, h)` **before** writing. Without it, painting over one cell of a 2×2 left the other 3 cells in `gridData`, and `checkSpots()` counted the orphans as a live facility → the spot stayed lit for a building the player had just destroyed. Wrong answers on the one thing this tool exists to answer, with no visible symptom.
- **Every destructive action goes through one guard.** Switching towns, pasting a load, opening a save, and clearing the canvas all route through the same dirty-check + `askModal` (`askName`/`askSave`/`askDiscard`/`askCancel`; `saveMapAs()` always confirms before overwriting a same-named save, and the prefilled name auto-avoids collisions). Guarding only some of them is worse than guarding none, because the unguarded path is the one people trust.
- **A share code that loaded must not stay in the URL.** After a successful `#m=` load, `history.replaceState` clears the hash — otherwise a reload silently discards every edit made since and restores the shared map.
- **Locate mode is a display state, not an overlay.** `setLocateMode(on)` is the only entry/exit point; it calls `clearSpotOverlays()` (all five spot channels: `.suggest`/`.suggest2`, the yellow core ring, `.spot-indicators`, `.spot-area-ov`, `.spot-tooltip`) and `updateSpotIndicators()`/`updateToolHint()` early-return while `body.locating`. Clearing without the source guard fails, because any edit re-runs `checkSpots()` and repaints them. Matched buildings get `.found` + numbered `.found-num` badges (capped at 40 — 146 grass cells numbered is noise, not information); badge clicks need a **capture-phase** `mousedown`/`touchstart` guard on `#gameGrid`, or painting swallows the click.
- **Zoom writes preferences; gestures must not.** `setZoom(z, anchor, transient)` — two-finger pan/pinch on `#mapContainer` (not `#gameGrid`: the first finger often lands on an axis label) passes `transient` so a pinch doesn't hammer `localStorage`, and rAF-throttles.
- **Every `track()` goes through `Shell.track`**, so behaviour events share the denominator with `page_engage` (which `mountBar()` does *not* send by itself — the sim sends it explicitly).

- **Placement suggestions**: `updateSuggestions()` marks empty tiles with a dashed blue outline (`.suggest`) where placing the currently selected building would complete a popularity spot — i.e., a 5×5 window already contains every other required item of some spot. Recomputed in `checkSpots()` and on `selectTool()` (which also toasts the completable spot names).
